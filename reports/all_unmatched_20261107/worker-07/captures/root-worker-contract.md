## Durable outputs

Keep working material in your assigned durable output directory or worktree
`.temp/`, never `/tmp`. Put publishable evidence under your own uniquely named
`reports/all_unmatched_20261107/worker-NN/` tree. Save new formal reviews with the
native `scripts/record_review.py inspect/validate/save` workflow; do not hand-write
its Markdown or change old reviews. Record exact input hashes and truthful base
provenance. Reuse immutable evidence by reference with its hash. Do not commit
virtual environments, caches, credentials, or unrelated large source archives.
For a source-only case with no MIM owner, assess the exact frozen source case;
never invent a YAML owner to satisfy a review format. If the native local profile
does not represent that assessment, state why it is not applicable and retain the
complete case decision, primary evidence and independent review in the campaign
contract. Do not report an unrun native validation as passed.

Maintain these outputs incrementally:

1. `acceptance.json`: worker/session identity available to you, actual branch and
   HEAD, assigned shard path/hash, output root, task phase and accepted UTC time.
2. `decisions.json`: one decision for every assigned `case_id` when the shard is
   complete. During the canary, include only the assigned canary case. Each entry
   must retain source identity/name, all occurrence references, current owner
   paths/hashes if any, disposition, detailed scientific reasoning, evidence IDs,
   existing issue decisions, proposal (or explicit no-change), exact unresolved
   requirement when applicable, and independent-review status. Safe lexical links
   are not identity merges. An explicit reviewed duplicate-group disposition must
   still account for each original source case separately.
3. `evidence.json`: immutable local primary-source captures/references, URLs,
   access UTC times, SHA256, exact relevant locator and what it supports or
   contradicts. Record unsuccessful searches and their actual scope for absence
   claims; include ignored files in repository absence searches.
4. `proposals.json`: exact proposed owner edits, before hashes, supporting cases
   and citations, identity/predicate/alias consequences, publication-review
   obligations, and any cross-shard conflict. Empty is valid when no edit is
   justified; give the reason in the case decisions.
5. `progress.json`: assigned/reviewed/remaining case IDs and counts, output paths,
   current task and real blockers. Scientific review and structural checks are
   separate. Do not label a sampled or automated lexical pass complete review.
6. A readable report, actual validation logs, independent review findings and
   their dispositions, and a SHA256 manifest of the final evidence bundle.

Allowed dispositions include existing identity/alias, proposed new distinct
ingredient, supplied-form correction, broad parent relation only, stock/product/
mixture context, malformed or nonchemical token, and unresolved with precise
missing evidence. Do not fill a shard with generic holds merely to reach a count.
Source insufficiency is a legitimate outcome only after inspecting its actual
context and pursuing relevant available primary evidence.
