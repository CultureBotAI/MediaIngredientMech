## Route B: a separate documented direct guarded curation phase

The native skills explicitly support a narrow mutator using `record_curation_event` and `write_validated_ingredient`. Existing `publication_guard` primitives and `reserve_receipt_outputs` support path/input binding, pre-reserved backups/receipts and completion rechecks. The native receipt maker's alignment and native verifier support owner-only edits with no canonical row changes. The actual in-memory probe extends the current 27-link chain with such a link and replays all 3,014 canonical rows exactly. This is contract evidence, not an applied receipt.

Therefore dependency-only edits do not inherently need campaign origins. A separate reviewed, bounded mutator may legitimately handle them with actual before/after owner hashes, scientific evidence, complete inventory accounting, prospective native owner-chain validation, unchanged canonical proof and a fresh approval-free receipt. The archived receipt maker CLI writes its output directly; it must not be invoked as an unreserved overwrite path. Reuse its native alignment semantics inside the supported guarded publication flow. The generic writer/receipt primitives are documented and available; no already-configured turnkey mutator for these twelve exact consumers was established by this bounded search.

The seven unsupported-ID withdrawals can be a standalone source-only phase without needing the future generic target. The five generic retargets cannot independently pass current cross-record validation until the specific local Peptone identity exists. That requires a deliberate final-overlay/phase plan, co-applying the target in the same separately reviewed phase, or deferring those five to an authentic campaign origin. Do not manufacture temporary identity rows, broaden a gate, or substitute `UNMAPPED` merely to simplify an otherwise settled generic retarget.

## Checkpoint and ordering rules

- `campaign_owner_apply.prepare` requires the exact baseline commit, clean tracked state, complete before inventory and current native chain. Its receipt captures canonical/prefix/history checkpoint bytes and the exact complete after inventory.
- `campaign_publication.prepare` calls the source verifier. It requires the source checkpoint to equal the publication's receipt prefix, historical context and canonical before hash. Its source completion recheck requires the exact after inventory.
- A separate dependency write cannot be inserted between campaign source application and campaign publication. It would change that complete inventory and correctly fail completion verification. Do not edit the source receipt, change hashes by hand, or pretend that the extra owner was in its accepted plan.
- If the separate phase comes first, finish its guarded source write and real native source-only receipt, synchronize/validate appropriate surfaces, then freeze a new campaign baseline/checkpoint/inventory. Original published proposals must still match each selected actual preimage. If an existing selected owner was touched, obtain a truthful successor rather than overriding its stale before hash.
- If the separate phase comes after a completed campaign phase, preserve the first phase's exact historical completion evidence; append a new native link and validate final source/row chains and fresh full semantic/companion evidence. The earlier campaign validator is no longer a claim about the later live full owner inventory. A concrete historical-phase replay and final closure plan would be needed; do not simply report that it still validates the final checkout.
- An owner-only receipt withdraws content-bound support through the existing native owner-chain rules. It does not approve component, mapping, role or export claims. Preserve all previous receipts and decisions; new support requires the existing fresh scientific review process.

No constructor, gate, policy, threshold or history change is proposed. The coordinator can choose the existing-constructor route or a concrete separately reviewed guarded phase; the plan must name its actual checkpoint and validator boundary before any write.
